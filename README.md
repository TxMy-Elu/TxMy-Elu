## À propos

Concepteur d'applications en alternance chez **BATIGERE** au pôle Études & Développement, et étudiant au **CESI** où je termine le CDA avant d'enchaîner sur le **MAALSI (2026-2028)** — le titre de manager en architecture et applications logicielles des SI.

Ma trajectoire va du code vers le **pilotage de projet informatique**, et je la revendique dans cet ordre. J'ai livré une application en production chez Sendix, j'ai été chef de projet sur deux projets CESI menés en équipe, et je travaille aujourd'hui sur le système d'information d'une entreprise. Un chef de projet qui a écrit le code, chiffré une tâche et vécu une mise en production discute autrement avec ses développeurs : c'est cette légitimité-là que je construis avant de piloter.

Côté technique, je construis des applications de bout en bout — modèle de données, API, puis l'interface que l'utilisateur touche réellement. Mon socle est le **développement full stack** : Laravel et Spring Boot côté serveur, React et Next.js côté client, Flutter en mobile, sur MySQL, PostgreSQL et Oracle. En entreprise, j'interviens aussi sur des chaînes de traitement de données en **SQL Oracle et ETL Talend**.

J'étends ce socle vers la **modélisation statistique et le ML appliqué** : [matchday-ai](https://github.com/TxMy-Elu/matchday-ai) prédit des résultats de matchs internationaux à partir de 49 481 rencontres historiques, en combinant ratings Elo, régression logistique multinomiale, GLM de Poisson et simulation Monte Carlo. Ce qui m'intéresse là-dedans, ce n'est pas le modèle pour lui-même, c'est de le rendre exploitable dans un produit.

J'aborde l'ingénierie avec un **état d'esprit produit** : une décision d'architecture se juge à ce qu'elle coûte à exploiter et à ce qu'elle permet pour la personne qui utilise le logiciel. Code lisible, frontières nettes, et des choses qui tiennent en production.

- Postes de concepteur développeur d'applications

## Projets

<details>
<summary><b>matchday-ai</b> — Prédiction de matchs internationaux · <i>Python · FastAPI · React</i></summary>

<br/>

Application web qui calcule les probabilités de victoire, nul et défaite entre deux sélections nationales, les buts attendus, la distribution complète des scores, et les chances de titre sur un tournoi. Le modèle s'appuie sur 49 481 matchs internationaux couvrant 1872 à 2026.

| | |
| :--- | :--- |
| **Stack** | Python, FastAPI, scikit-learn, statsmodels, NumPy · React, Vite, Tailwind CSS |
| **Modèle** | Elo (K pondéré par importance : 60 en finale de Coupe du monde, 20 en amical) → régression logistique multinomiale pour V/N/D · GLM de Poisson pour les buts domicile/extérieur · correction Dixon-Coles sur les petits scores · Monte Carlo 20 000 tirages |
| **Données** | 49 481 matchs internationaux (1872-2026), normalisation des anciens noms de sélections, résolution des séances de tirs au but |
| **Évaluation** | Backtest temporel (entraînement < 2018, test sur 8 210 matchs postérieurs) : **log-loss 0,874** contre 1,051 pour les fréquences de base et 1,099 pour l'uniforme · **Brier 0,514** · **60,1 % d'exactitude** · **erreur de calibration 0,012** |
| **Architecture** | Entraînement offline (`train.py`) produisant un artefact `team_ratings.json` ; l'API sert les prédictions en maths fermées, sans aucune dépendance ML au runtime |
| **Déploiement** | [matchday-ai.vercel.app](https://matchday-ai.vercel.app) — frontend statique sur Vercel, backend FastAPI |
| **Dépôt** | [![Repo](https://img.shields.io/badge/Voir-4c1d95?style=flat-square&logo=github&logoColor=white)](https://github.com/TxMy-Elu/matchday-ai) |

La décision structurante est la séparation entraînement / service. Les coefficients sont figés dans un artefact JSON à l'entraînement, ce qui permet à l'API de ne dépendre que de NumPy et de maths pures : démarrage immédiat, empreinte minimale, comportement déterministe et reproductible. Le choix d'un modèle statistique explicite plutôt qu'un gradient boosting est délibéré — chaque probabilité sortie est traçable jusqu'à un paramètre interprétable, ce qui compte quand on affiche un pourcentage à un utilisateur.

Le modèle est évalué par backtest temporel (`evaluate.py`, reproductible) et non par split aléatoire : un rating Elo de 2010 contient déjà les matchs de 2015, donc un split aléatoire ferait fuiter le futur dans le passé et produirait un chiffre flatteur et faux. Les résultats tiennent sur quatre dates de coupure (2010, 2014, 2018, 2022), avec une erreur de calibration stable autour de 0,012 — quand le modèle annonce 75 %, l'événement se produit 74,7 % du temps.

</details>

| | |
| :--- | :--- |

| **Stack** | Java (API) · TypeScript (web) · Dart / Flutter (mobile) |

| **Portée** | Une API centrale et deux clients distincts consommant le même contrat |
| **Dépôts** | [![api_zen](https://img.shields.io/badge/api__zen-4c1d95?style=flat-square&logo=openjdk&logoColor=white)](https://github.com/TxMy-Elu/api_zen) [![cesizen_web](https://img.shields.io/badge/cesizen__web-4c1d95?style=flat-square&logo=typescript&logoColor=white)](https://github.com/TxMy-Elu/cesizen_web) [![cesizen_mobile](https://img.shields.io/badge/cesizen__mobile-4c1d95?style=flat-square&logo=flutter&logoColor=white)](https://github.com/TxMy-Elu/cesizen_mobile) |

L'intérêt technique du projet est la contrainte du contrat d'API : deux clients écrits dans des langages différents consomment la même surface, ce qui interdit de rattraper une faiblesse de conception côté serveur par un contournement côté client. La discipline se joue à la frontière.

Côté pilotage, c'est précisément cette contrainte qui structurait la coordination : trois plateformes développées en parallèle par une petite équipe, où le contrat d'API devait être figé avant que les clients avancent. Le vrai travail de chef de projet était là — séquencer pour que personne n'attende, et faire tenir la décision d'interface au bon moment.

</details>
